# ClipBridge 安卓更新、界面与免密钥发现设计

日期：2026-11-02

状态：用户已于 2026-11-02 确认，按本方案实施 0.5.0。配套效果图仍为设计稿，不能当作真机截图。

## 目标与现状

用户使用一加 15，希望手机版具备自动更新、更完整美观的界面，以及自动搜索附近可连接设备的能力，首次连接不必输入 64 位密钥。继续遵守此前约定：剪贴板只在应用前台主动预览、发送；文件必须主动接受；不使用 Shizuku、ADB 或输入法；后台事件及开发检查不能打断游戏。

当前 Android 0.4.0 没有更新检查或安装入口。现有 UDP 公告使用配对密钥加密，BridgeService 在没有密钥时直接退出，导致新设备不能先发现再配对。Windows 和 Android 的业务目前各使用单个共享密钥，因此新增多设备信任需要两端一起改造。

本次的“附近”指同一 Wi-Fi 或手机热点内、正在运行 ClipBridge 的设备。蓝牙发现、跨互联网连接及云端中继不在范围内。网络隔离、VPN 或防火墙可能阻止发现，应提供明确提示和手动 IP 后备入口。

## 方案比较

1. 推荐：公开局域网发现 + 两端核对短验证码 + 每台设备独立密钥。复用现有 UDP 端口和 TCP 业务通道，补充配对通道及版本标识。首次无须手填密钥；需要同步升级 Windows；旧协议作为独立兼容路径保留。
2. mDNS/DNS-SD + 相同的安全配对。系统标准化程度更高，但 Windows 需新增服务发现适配，且路由器仍可能过滤组播。现有 UDP 已有基础，本次优先使用第一种，之后可增加 mDNS。
3. 二维码配对。适合网络发现不可用时补充，但需要摄像头与扫码流程，不能单独满足自动发现。因此本次不引入。

## 用户可见流程

打开手机应用即开始搜索；未配对也能显示“附近设备”。首页分成“我的设备”和“附近设备”，卡片显示设备名、系统、状态、地址以及连接操作。

首次点电脑卡片的“配对”，电脑只增加一个待处理请求，不自动打开窗口。用户主动打开电脑面板后查看验证码。手机和电脑显示同一组 6 位数字，核对后分别点“确认一致”；两端都确认才保存信任，任意一端拒绝、数字不一致或超时则丢弃会话。

已配对设备在同一网络重新出现时自动恢复连接。选择目标后才能发送文件或剪贴板。多台电脑分别保存信任材料，可单独取消配对。离线设备保留在“我的设备”，明确显示离线且禁用发送。

旧版 Windows 继续支持已有的手动密钥配对；入口放在设置的“兼容旧版 / 手动连接”中，不再占用首页。新发现和免手输配对需要新版 Windows 配套支持，不能宣称旧 Windows 自动具备此能力。

## 安卓界面

采用清爽的浅色卡片布局，深蓝主操作、薄荷绿连接状态、清楚的字号层级、统一圆角和线性图标；提供对应深色主题并跟随系统。底部固定三个入口：设备、传输、设置。兼顾大字体、窄屏、系统边距、48dp 点击区域和读屏描述。

设备页：顶部应用名和连接状态；突出当前选择的目标设备；“发送文件”和“发送剪贴板”两个主要操作；下面是附近设备与搜索状态。没有设备时显示同网检查建议和重试入口，不显示密钥输入框。剪贴板只在用户点击后读取；预览中的“确认发送”才创建发送消息。

传输页：待接受请求优先；每张卡片显示设备、文件名、数量、可读大小、进度、状态和接受 / 拒绝 / 取消操作。完成项可定位接收文件。文本只记录发送方向、时间与状态，不保存或显示历史正文。若提供历史，持久化数据必须有数量上限与清除入口，不记录完整敏感路径。

设置页：本机名称、连接服务开关、接收目录、自动更新设置、当前版本、检查更新、已信任设备管理，以及折叠的旧版配对入口。拒绝通知权限不阻止进入首页；必要权限只在用户相关操作时请求。

## 自动更新

复用已有 latest-v2.json RSA 签名信封及 Android 元数据，不另建无签名渠道。内置当前发布公钥；验证 payload 原始字节的 SHA256withRSA 签名后才解析 Android 更新信息。检查包名、严格递增的 versionCode、版本字段、HTTPS 下载地址、大小、SHA-256 与既有签名证书指纹。

应用打开时若距离上次成功检查已满 6 小时，则静默检查；提供可关闭的每 24 小时一次后台检查。后台任务由 Android 系统调度，遵守网络和电量条件，不保证精确到点。默认仅在非按流量计费的网络自动下载；用户可关闭自动下载或手动检查。检查和下载仅改变应用内状态，不触发声音、横幅、弹窗、Activity 或安装器。

主清单地址为 GitHub Raw；连接失败时回退到同一仓库的 GitHub Contents API，受大小限制地 Base64 解码出原始签名信封，并执行完全相同的验签。缓存只能保存已验证信息。签名无效、包名不符或已拿到清单但校验失败时拒绝更新，不借回退跳过校验。

下载写入应用私有目录的 .part 文件；使用限制重定向的 HTTPS 下载并检查最终地址，计算实际长度和 SHA-256，成功后验证 APK 的包名、versionCode、完整签名证书集合和与当前安装包一致的签名身份，再原子替换为待安装包。失败、取消或磁盘不足时清理不完整文件；更高版本出现时废弃过时包。

下载完成显示应用内“更新已就绪”。只有用户主动点“安装更新”才请求安装权限并移交系统安装界面；普通侧载应用不能承诺在所有 Android / ColorOS 版本上无确认静默覆盖安装。若系统要求允许此来源或确认安装，按系统流程处理。重新回到应用时重查当前版本和安装权限，避免重复弹出安装器。

Android 官方安装接口依据：https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int)

现有 0.4.0 没有更新模块，无法靠远程清单自行获得本功能；首次升级仍需手动安装一次同签名新版 APK，之后使用新版内的检查、下载及安装入口。固定发布证书不变，不要求卸载正式版或重新建立已有配对。

## 未配对发现与认证边界

公开发现包使用明确的新版本前缀和严格 JSON 格式，与旧版加密公告区分。只发布协议版本、随机设备标识、用户设备名、系统类型、固定服务端口和有限能力标记；不包含密钥、剪贴板、文件名、接收路径或真实账号。

对有效本地 IPv4 接口发送定向广播，同时接收搜索请求并限速单播响应。网络改变时重新枚举接口并刷新端点。限制单包长度、字符串长度、最大设备数量和响应频率；以短期过期时间清理离线公告。来源 IP 来自实际数据包而非可信任公告字段。

公开公告仅表示“发现”，不能据此标为“已信任”或更新信任记录。已经配对的设备必须完成持有密钥的挑战应答，或通过已有密钥认证的业务连接，才显示为可发送；同名、伪造 DeviceId 和更换 IP 均不能绕过认证。

手机搜索只在用户已开启连接服务或前台探索期间工作。Windows 延续托盘静默启动；网络接收不打开窗口。新配对待办在两端都只进入应用内列表。

## 配对与密钥

新增独立 TCP 配对通道，固定使用 45824；沿用局域网来源限制，最多 4 个会话并发、单设备限速、有限总待办和 120 秒超时。手动 IP 也走相同认证流程，不自动信任。

使用系统密码库的临时 P-256 ECDH 和 HKDF-SHA256 建立会话。双方先对临时公钥、会话 ID、角色、设备标识和随机数做承诺，再互相揭示并验证承诺；不能在看到对方揭示值后重新挑选本端材料。将完整、有固定序列化规则的会话转录绑定到验证码、会话密钥和确认消息，防止中间人自由替换或重放。验证码为短认证串，只有用户实际比对并两端确认才建立信任；不把数字相同之外的界面行为误当授权。

双方在已认证的临时加密通道内分别发送确认；收到两端有效确认后，由发起端生成 32 字节随机长期配对密钥，通过该通道提交。接收端写入待完成记录并返回持有密钥的提交确认；发起端保存记录并发送最终确认。只完成其中一步的记录保持不可发送状态，并在同一密钥认证的恢复握手完成后才启用；超时残留记录可被用户取消，不能自动升级为信任。超时、取消、拒绝和关闭服务都销毁临时私密材料。实现计划中必须固定所有线格式和互操作向量，不自行实现椭圆曲线算法。

新信任记录按对端设备标识分别保存，Android 使用 Keystore 包装，Windows 使用 DPAPI。新设备之间每对独立随机密钥，取消一台不会影响其他设备。已有共享密钥作为明确标注的 legacy 记录保留；旧版共享信任不是可单独撤销的独立密钥，不将其伪装成逐设备安全隔离。新配对不广播或自动导出旧的全局共享密钥。

文字与文件通道保持原端口；新帧带版本与来源 / 目标路由标记，并将路由头纳入 AEAD 的认证附加数据，从本地信任记录选择唯一密钥。未经认证的标识只用于查表，业务来源必须在认证完成后才可信。旧帧仍走旧密钥路径；不能通过伪造新头回退后获得业务权限。每设备分别派生文字、文件、在线认证密钥，使用不同域标签与随机 nonce。

撤销新信任记录后立即停止该设备的新发送并关闭对应连接，后续通信必须重新配对。仅修改公告或 IP 不能恢复已删除的信任。

## 组件边界

Android 将 MainActivity 的布局和业务调用拆成设备、传输、设置三个页面，以及独立的状态模型；界面不直接进行网络或磁盘操作。

DiscoveryService 只负责发现候选设备；PairingProtocol / PairingCoordinator 只负责首次确认；TrustedDeviceStore 负责安全存储与迁移；BridgeService 管理经过认证的连接；UpdateProtocol / UpdateRepository / 更新后台任务负责验签、调度与下载。Windows 提供相同的发现和配对协议实现，并在现有控制面板增加待配对列表。

传输、剪贴板及文件存储流程继续使用已有模块，针对逐设备密钥作最小必要调整，不顺带重写安装器、发布签名或整个 Windows 界面。

## 验证与交付

1. 双端发现解析：未配对可发现、来源限制、坏包、超长包、过期与重复、设备伪造、限流和接口变化。
2. C# / Kotlin 配对互操作：同一验证码和密钥、正常双确认、任意一端拒绝、未确认、承诺篡改、重放、会话调换、超时、取消、断网及半完成记录恢复。
3. 多设备与兼容：新设备逐对隔离、取消其中一台、地址变化、旧共享密钥迁移、已有文字和文件协议回归。
4. Android 更新：有效与无效签名、错误包名 / 版本 / 证书 / 长度 / 哈希、受限下载、网络失败与回退、损坏缓存及取消清理。使用合成测试包或已有签名样本，绝不泄露发布私钥。
5. 无界面构建：Windows 主工程、TransferTests、两个 smoke test 项目只编译；Android 单元测试、Lint 和构建；发布脚本合成测试与安装器策略检查按 AGENTS.md 运行。完成后报告实际执行结果，不将构建通过说成真机通过。
6. 一加 15 的系统安装确认、ColorOS 后台调度、不同字体与主题、真实 Wi-Fi / 热点以及 Windows 防火墙仍需方便时实测。开发期间不打开程序、安装器、模拟器或浏览器预览，也不修改用户防火墙。

实现完成后准备同签名 APK 和配套 Windows 安装包，保留正式 GitHub 发布管线。新版本号尚未选择；设计确认不等于可以覆盖历史资产。正式发布前按现有不可变版本规则完成构建、签名及包验证。
